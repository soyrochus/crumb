Retargeting Crumb

From “a view-only file explorer that happens to demonstrate Bun” to what it has actually been all along: the template, toolchain, and documentation for shipping server-less web apps as desktop apps.

Analysis · repository review 28 Aug 2026 1,662 LOC reviewed

What Crumb is

Crumb is the template. It stays called Crumb.

Crumb is everything you need — project template, build toolchain, and documentation — to take a web app that runs entirely in the browser, with no server, and ship it as a real desktop application: one native window, one self-contained executable, no Chromium, no localhost, no runtime install.

The three-pane file browser is not Crumb. It is file-explorer — the example app that proves the template works, and the first thing a newcomer deletes.

Crumb is

A repository you clone. A Bun-based build pipeline that bundles a browser UI, embeds it in a host, and compiles the pair into one binary. A validated RPC boundary between page and host. Native-WebView plumbing per platform. The docs that make all of it reproducible.

Crumb is not

A file manager, a product, or a framework you install from a registry. Nothing in file-explorer — directory listing, previews, the three-pane layout, the read-only rule — is part of what Crumb promises.

Everything below follows from that one sentence. The rename is not cosmetic: it decides which code is a promise and which code is a demonstration — and which constraints Crumb is entitled to claim.

The finding

The repository is already about three-quarters template. The problem is labelling and file-level entanglement, not architecture.

Of roughly 1,660 lines, about 380 are genuinely reusable shell and build machinery, and about 900 are file-explorer domain. But the two are not separated by directory — they are mixed inside single files:

  • src/host/main.ts is window bootstrap, CSP, and the message loop — all reusable — plus the wiring of four explorer handlers, in one 57-line file.
  • src/shared/contracts.ts puts Result, DomainError, and RpcMethods beside DirectoryListing and ImagePreview.
  • src/shared/validation.ts is the sharpest case: validateRpcInput is a hardcoded if chain over those same four explorer methods. A template needs a per-method validator table that the app registers.

So this is extraction, not redesign. The RPC boundary, the virtual-module embedding, and the two-stage compile are already the right shapes — they just have a file explorer sitting on top of them.

Scoping

Three requirements are filed under the wrong owner — and the leak runs both ways

The file explorer is view-only because that simplified its implementation, and it should stay exactly that way. It is a property of file-explorer, not a property of Crumb — a template for desktop apps cannot promise that the apps built with it never write files. The specs mostly agree already: filesystem-browsing files “Read-only filesystem implementation” as its own requirement, which is the right home for it.

But writing the change proposal turned up two more mis-filings, and the second runs in the opposite direction — an example capability holding a promise every Crumb app needs. Together they are the substance of the split.

Read-only is claimed by Crumb, but belongs to the example

  • openspec/specs/desktop-shell/spec.md — “Narrow read-only RPC surface” sits in a template-level spec and enumerates the explorer's four methods. What belongs at template level is that the UI reaches the host only through declared, validated methods; whether those methods write is the app's business.
  • README.md — “Crumb's core constraints: view-only filesystem access, …”. View-only is the example's constraint.
  • scripts/verify-readonly.ts globs src/{host,shared}/** repo-wide and package.json exposes it as a top-level script. Scope the glob to the example, or every app built on Crumb inherits a check that fails the moment it writes a file.

The Content Security Policy is held by the example, but belongs to Crumb

three-pane-interface — otherwise entirely example UI: panes, separators, keyboard model, appearance — owns the requirement “Restrictive document policy.” Nothing in it describes a pane. It is the CSP that blocks remote connections, frames, object embedding, and forms in any embedded document, and every app built on Crumb needs it.

Left where it is, an app that deletes the example deletes its own document policy. It moves to desktop-shell as a template default an app may widen only by explicit declaration.

The distribution spec names Crumb and the explorer's journey

standalone-distribution is almost entirely template — two-stage build, target matrix, single-file executable, artifact inspection — but two requirements leak. “Permitted operating-system dependencies” says Crumb forces the Wayland GDK backend, when it is the built application that does. And “Clean-machine acceptance” hardcodes an explorer-shaped journey: navigate directories, preview text, preview an image, handle an unsupported file. That is the example's acceptance test wearing the template's clothes; the template's version is that an app completes its own declared interactions.

None of this weakens a guarantee. The explorer stays view-only, the CSP stays exactly as strict, and the clean-machine journey still runs — the requirements simply move to the capability that owns them, so the extraction has a boundary to be checked against.

Two details make this earn its keep.

Ship the minimal example, and make it the default

Right now the first thing a newcomer meets is 900 lines of file explorer. The template's real teaching surface is about 40 lines. Ship both, and point bun run dev at minimal.

Rename the virtual modules

crumb:ui and crumb:native should become app:ui and app:native in scripts/dev.ts, scripts/build.ts, and src/ui/virtual.d.ts. Crumb keeps its name as the project; it should not keep its name inside every downstream app's build plumbing. This is the one place where the naming decision cuts the other way.

Friction, ranked worst first

What actually stands between a clone and a running app

  1. The Linux native path

    A clean clone on Linux downloads a source archive, checksums it, applies a patch at zero fuzz, and runs cargo build --release — requiring Rust, a C toolchain, and GTK/WebKitGTK development headers. Superb as a demonstration of Bun's process API; brutal as “quickly start an app.” Vendor or prebuild the patched addon, or publish it once as a release asset and fetch the binary.

  2. No watch mode

    scripts/dev.ts is one-shot: edit the UI, close the window, run again. For a template positioned on speed, rebuild-and-restart on change is table stakes.

  3. No CI

    .github/ contains only OpenSpec prompts — no build, no test run, no release matrix. A template people trust needs a green badge that means something.

  4. The platform matrix

    No Windows; Linux is Wayland-only; macOS is arm64-only. Honest limits for a demo, hostile ones for a template — “does it do Windows?” is the first question every visitor will ask. It need not be solved now, but the README must lead with the answer and a roadmap position instead of burying it.

  5. DevTools are hardcoded off

    devtools: false sits in src/host/main.ts. It should follow dev versus release. Small fix, disproportionate effect on the first hour of building an app.

Against

Three things worth not doing

  • Don't publish the kit to npm.

    The value here is the build pipeline — Bun compile, virtual modules, native-addon embedding. Package registries distribute runtime code well and build pipelines badly. Clone-and-rename is the right distribution model, which is also why Crumb stays a repository rather than becoming a dependency.

  • Don't delete the file explorer.

    It is the proof the thing works, the source of both screenshots, and its 36 tests are the only evidence the RPC boundary holds. Demote it to examples/file-explorer/; do not discard it.

  • Don't rewrite the OpenSpec specs — split them.

    desktop-shell, standalone-distribution, and the RPC-boundary requirements are Crumb's own product requirements and stay. filesystem-browsing, file-preview, and three-pane-interface become example-app specs. That split is itself a clean change proposal.

Sequencing

Three changes, not one

  1. Retarget the purpose and split the spec set

    Documentation only, no code. States plainly that Crumb is the template for server-less web apps as desktop apps, and re-files the three mis-owned requirements before a single file moves. Proposed as retarget-crumb-as-template: one new template-identity capability, four spec deltas, and the five TBD Purpose placeholders finally filled. Verification is blunt — zero files changed under src/, scripts/, or test/, and all four existing commands pass unchanged.

  2. Extract the kit

    src/kit/, app.config.ts, renamed virtual modules, and the explorer relocated to examples/file-explorer/ intact — with all 36 tests still green as the acceptance condition.

  3. The developer-experience layer

    Minimal example, watch mode, dev DevTools, CI with a release matrix, and a prebuilt Linux addon.

Change 1 is the one that deserves real attention. Changes 2 and 3 are largely mechanical once the invariant is settled.
